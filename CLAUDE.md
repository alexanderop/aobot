## Commands

- `vp run check`: `vp check` (format, lint with our plugins, type-check), then `vp test run` (`unit`, `architecture`), then knip. Run it before calling anything done. Works today.
- `vp install`: installs with the pinned pnpm. `vp fmt` formats. `vp check --fix` formats and autofixes.
- Imports: tests use `vite-plus/test`, lint plugins use `vite-plus/lint/plugins` (enforced by `vite-plus/prefer-vite-plus-imports`).
- `vp run test:smoke` (from E0-3): one turn against the real model in `MODEL_*`. Not part of `check`; runs nightly.
- `vp run test:contract:agents` (from E0-5): agent runtime contract suite (`*.contract.ts`): `api` and each `acp` CLI against the mock model server, streaming, cancel, and no shell or file access outside the gateway. Starts the real pinned adapters through `npx`. Not part of `check`.
- `vp run test:contract` (from E1-1): computer provider contract suite. Builds `aobot-computer:dev` from `apps/computer/Dockerfile` and runs it against a local fixture. Needs Docker. Not part of `check`; CI runs it.
- The computer image (from E1-1): `docker compose up --build` builds `aobot-computer:dev` through its `computer-image` service. A server on the host needs it built by hand: `docker build -f apps/computer/Dockerfile -t aobot-computer:dev .` from the root.
- `vp run dev:acp` (from E0-5): builds the web app and serves it on http://localhost:3100 on your own Claude Code subscription over `acp`, with the CLI signed in as usual. The Bot's computer needs the image above. `ACP_AGENT=codex vp run dev:acp` for Codex, `PORT=…` to move it. `acp` refuses to start without single-user mode on loopback, so it never runs in compose.
- `vp run verify <ticket-id>` (from E0-1): the ticket's demo in a real browser with `agent-browser`. A slice is done only when this passes. Its stack publishes the server on 3100, Grafana on 3400 and Dex on 5656, so it runs beside `docker compose up`. From E3-1 a scenario starts signed in as alice at Dex, unless it exports `signedIn = false`. A scenario that exports `stack = false` runs without the stack.
- `docker compose up` (from E0-1): the server (SQLite file on a volume only it mounts, `bots.yaml` mounted read-only from the root from E2-1, `rules.yaml` from E2-2), `grafana/otel-lgtm` (Grafana on http://localhost:3300, traces under Explore → Tempo from E0-2, opened from each row of the audit page at http://localhost:3000/audit through `GRAFANA_URL` from E2-4), and from E3-1 Dex on http://localhost:5556, where you sign in as alice@example.com, bob@example.com or mallory@other.com (refused: only example.com may sign in), each with the password `password`. From E1-1 the server mounts the Docker socket and starts the computer (`aobot-computer`) itself, on the `aobot_computers` network it shares only with the server and the collector.
- `vp run people:remove <email>` (from E3-1): removes a person from the database in `DATABASE_PATH` with the sign-in settings the server has: their sessions end at their next request, their address is blocked, and a `person.removed` row is written. In Compose: `docker compose exec server node apps/server/src/app/remove-person.ts <email>`.

## Rules

- Work in vertical slices: one ticket, every layer it needs, ending in its demo. Follow `docs/ticket-template.md`.
- Feature-based: `src/app`, `src/features/<feature>/public.ts`, `src/shared`. Register a feature in `tools/oxlint/aobot-architecture/policy.ts` before creating it.
- Every action a Bot takes goes through the gateway: only the `gateway` feature may depend on `computers`.
- Every Bot turn starts through `Turns.start` in `features/lifecycle`, whoever asks for it, so a paused Bot never runs anywhere. Never run an agent turn around it.
- A Bot's tools are what `bots.yaml` grants it, and `Gateway.act` checks the grant first, after only the check that the call's turn still runs. Every Bot is still offered the whole toolkit; never filter it per Bot instead.
- An audit row's `action` is an `AuditAction` from `packages/domain/src/audit.ts`, which says how each reads. A new action joins that list with its label.
- An action on the safety list in `gateway/safety.ts` is handed to the person after its ref resolved and before any rule. The list is code, never configuration, and a new tool decides in `safetyOf` whether it is subject to it.
- Every action the gateway allows is allowed by a rule in `rules.yaml`, judged after its ref or path resolved. An ask rule only narrows: it is read after an allow rule held, and its question and answer go through `gateway/approvals.ts`. A new fact a rule can read goes into `Facts` in `features/policy/facts.ts`, bound on every action; a new refusal is one more tagged error in the gateway's `Denial` union, worded in its branch of `refused`. A move of the approvals ledger commits with the audit rows that record it, in one transaction.
- Settings only through Effect `Config`. No `process.env` elsewhere.
- Who a request is for comes only from the HTTP gate and the `SignedIn` RPC middleware: `CurrentActor` in `shared/actor.ts` carries it to the rows it writes, and an RPC handler that acts for the person reads `Caller`. Every RPC group carries `.middleware(SignedIn)` (`app/rpcs.test.ts` checks it). A turn is the one hand-off: `Chat.send` passes its `PersonActor` to `Turns.start`, and the gateway reads it back from `LiveTurns` for each of the Bot's calls. Nothing takes an actor id as a parameter.
- Never write what a Bot typed into a page, or a secret a person gave it, into audit rows, logs, spans or the conversation. Use `shared/redact.ts`: `redact()` for typed text, `redactUrl` for an address, `redactUrlSecrets` for an address the model reads, `redactCommand` for a `run` command's audit row (never a span or a log). A secret is a `Redacted` from the RPC to the computer's `fill`.
- Effect v4 conventions: `Context.Service`, `Layer.effect`, `Effect.fn("Domain.operation")`, `Schema.TaggedError`. See the `effect` skill.
- When a ticket is done, set `status: done` in its front-matter and add its `verify` scenario in the same change.
- The UI follows `docs/design.md`.
- Every PR description follows the `pr` skill (`.claude/skills/pr/SKILL.md`): Summary, Evidence, Merge Danger.
- The web app is React with `@effect/atom-react`: state in atoms, read through a few hooks. See `docs/architecture.md` § The web app.

When asked about a library listed below, explore its source there first instead of guessing or relying on training data.
